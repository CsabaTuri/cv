# Security Policy

[Magyar verzió](./SECURITY.hu.md) · **English**

## Supported versions

This is a demo project without releases. Only the tip of `main` is maintained;
anything older is not. The images published by CI are immutable per-commit builds
(`ghcr.io/csabaturi/*:sha-<7-char commit>`), so a published image is never
patched in place — a fix lands in a new commit and a new tag.

| Version | Supported |
| --- | --- |
| `main` (latest commit) | ✅ |
| Older commits, older `sha-*` images | ❌ |

## Reporting a vulnerability

Please report privately by email to **csabaek@gmail.com**, with `[security] cv:`
at the start of the subject. Include as much of this as you can:

* what the issue is, and which component it affects (`cv/`, `chat-backend/`,
  `deployer/`, the Compose files, the CI workflow);
* the steps to reproduce it, or a proof of concept if you have one;
* the impact you believe it has — what an attacker gains;
* anything you already tried, and how you would like to be credited.

**Please do not** open a public issue, a discussion or a pull request for a
vulnerability, and please do not include anybody's personal data or a live secret
in your report. If you believe a secret has been committed to this repository,
report it the same way instead of opening an issue.

## What to expect

| | |
| --- | --- |
| First reply | within 72 hours, best effort |
| Assessment | whether it reproduces, the severity, and a rough plan — usually within a week |
| Fix | on `main`, with the commit or pull request noting your report if you want credit |
| Disclosure | coordinated; see below |

This is a spare-time project, so there is no bug bounty and no guaranteed fix
window. Honest reports still get an honest answer.

## Responsible disclosure

* Give a reasonable window — 30 days is a good default — before writing about the
  issue publicly.
* Do not go further than you need to prove the issue: no data exfiltration, no
  persistence, no lateral movement, and no denial of service or automated
  scanning against the live site.
* The demo deployment may be reset or taken down at any time; do not rely on it
  keeping anything you leave behind.
* Do not test against accounts, conversations or data that are not yours.

## Scope

In scope — the code in this repository:

| Area | Examples of what is interesting |
| --- | --- |
| `chat-backend/` | Admin authentication, the chat endpoints, the push subscriptions, SQL handling |
| `cv/` | The static export, the service worker, the PWA manifest, `/api` proxying |
| `deployer/` | The rebuild endpoint behind the admin panel — it holds the Docker socket, so privilege boundaries matter here |
| `docker-compose*.yml` | Container hardening: capabilities, read-only filesystems, network isolation, published ports |
| `.github/workflows/ci.yml` | Secrets handling, what a pull request is allowed to run |

Out of scope:

* GitHub itself, and GitHub Actions as a platform — report those to GitHub.
* Vulnerabilities in upstream images or dependencies (`mysql`, `phpmyadmin`,
  `nginx-unprivileged`, Node, npm packages) that are not made worse by how this
  project uses them; report them upstream, but a note is welcome if the way we
  configure them matters.
* Findings that require an already-compromised host, a malicious browser
  extension, or physical access.
* The `ADMIN_TOKEN` and the database passwords in a local `.env` — those are
  generated by the operator and are supposed to be secret; `.env` is never
  committed.
* Missing hardening, rate limiting or monitoring on the public demo, unless it
  leads to a concrete attack. It is a demo — say so in the report and it will be
  taken seriously anyway.
* The chat itself being unauthenticated for visitors: it is meant to be open, and
  the API has a 32 kB request body limit but no rate limiting. Spam and abuse on
  a public demo are known limitations, not vulnerabilities.
